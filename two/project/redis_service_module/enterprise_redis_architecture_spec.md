# 企业级 RAG 系统 Redis 应用场景

**业务背景**:多品牌智能客服知识库,用户提问 → 检索知识库 → LLM 生成回答。日活跃用户量大,知识库按品牌/渠道做了 metadata 隔离。

---

## 一、RAG 请求全链路中 Redis 的介入点

```
用户提问
  │
  ▼
[1] 分布式锁:防止同一用户重复提交同一问题
  │
  ▼
[2] Token 配额检查:DECRBY 预扣减,余额不足直接拒绝
  │
  ▼
[3] 热点问题缓存查询(命中→直接返回,跳过后续所有步骤)
  │  未命中
  ▼
[4] 检索前置:Query 改写结果缓存(同一用户短时间内重复问法命中改写结果,省一次 LLM 调用)
  │
  ▼
[5] 调用 Milvus/ES 做向量+关键词混合检索
  │
  ▼
[6] 检索结果缓存(同一 query + 同一 brand/channel metadata 组合,缓存召回的 chunk id 列表,不缓存最终答案)
  │
  ▼
[7] 组装 Prompt(含会话历史,从 Redis 会话缓存里取近 N 条)
  │
  ▼
[8] LLM 流式生成(通过 Redis Stream 解耦网关与推理 Worker)
  │
  ▼
[9] 生成结束后:
    - 释放分布式锁
    - 用实际 usage.total_tokens 扣减配额
    - 异步写回会话历史
    - 判断是否满足"热点问题"条件,写入 [3] 的缓存(需要命中率统计支撑,不是所有问答都值得缓存)
```

---

## 二、关键点摸索方向

### 1. [3] 和 [6] 的缓存粒度不同,容易混为一谈

- **[3]**:缓存的是"完整答案",风险高(时效性、个性化问题),只适合极高频、内容稳定的 FAQ(如"保修期是多久")。
- **[6]**:缓存的是"检索到的 chunk id 列表",风险低很多。即使问法有细微差异,只要召回结果一样就能命中,LLM 生成部分依然实时跑,答案的时效性和个性化不受影响。
- **建议路径**:先只做 [6],观察命中率和收益,再决定要不要碰 [3]。

### 2. [3] 什么时候值得做,怎么判断"值得缓存"

- 需要先跑一段时间的 query 日志,统计高频问题分布。可以用 Redis ZSet 做实时 Top-N 统计:

```sql
ZINCRBY hot_queries 1 <query_hash>
ZREVRANGE hot_queries 0 50 WITHSCORES   -- 取当前 Top 50
```

- 只有进入 Top-N 且内容确定不涉及时效/个性化的问题,才灰度进入 [3] 缓存。
- 这一步的产出物应该是一份"缓存准入规则",而不是无脑缓存所有问答。

### 3. [4] Query 改写缓存的 key 怎么设计

- 直接用原始 query 做 key,命中率会很低(用户问法千差万别)。
- 可摸索方向:
  - 先做简单归一化(去停用词、统一大小写、去标点、繁简转换)。
  - 归一化后的文本做 hash 当 key,而不是拿原始长 query 做 key(节省内存、避免特殊字符问题)。
  - 观察归一化前后的命中率差异,决定是否需要引入更复杂的语义级归一化(比如向量聚类归并相似 query,再决定是否有必要,别一上来就上重方案)。

### 4. [6] 检索结果缓存的失效策略

- Key 需要同时包含 `query_hash + brand + channel`,缺一不可,否则会出现跨品牌串结果的问题。
- 知识库文档更新(增删改)时,如何让相关的检索结果缓存失效?
  - 方案 A:粗暴地设置较短 TTL(如 10-30 分钟),牺牲一部分命中率换取简单性。
  - 方案 B:知识库更新时按 brand/channel 维度批量删除对应前缀的 key(需要维护一个可以按前缀 `SCAN` + `DEL` 的清理任务,注意 `SCAN` 在生产环境要控制批次大小,避免阻塞)。
  - 可以先上方案 A 跑起来,再评估是否需要方案 B 的精确失效。

### 5. [7] 会话历史的截断策略

- 存全部历史还是只存近 N 条?建议只存近 N 条(比如最近 10 轮),超出部分归档到 DB,Redis 只做"热数据窗口"。
- N 的大小要结合 LLM 上下文窗口和 Token 成本一起权衡,不是越大越好。

### 6. [8] Stream 解耦是否真的需要

- 如果当前网关和推理 Worker 是同进程/同容器,这一层解耦收益有限,可以先跳过,等真正出现扩缩容需求(比如推理压力大导致 SSE 连接堆积)时再引入,避免过早引入分布式复杂度。

### 7. [9] 缓存回写的时序问题

- 释放锁、扣减配额、写会话历史、判断是否进入热点缓存,这几步谁先谁后、哪些必须同步哪些可以异步,直接影响并发安全性和用户体验(比如锁释放太晚会导致用户明明看到答案却提示"处理中")。
- 建议:锁释放尽量提前(生成完成即可释放,不用等后续所有异步任务完成),配额扣减和会话历史写入可以异步化,避免拖慢主链路响应。

---

## 三、防坑提醒(结合你们现有架构)

- 你们已经有 Milvus + ES 双写,[6] 的检索结果缓存只是缓存"结果引用"(chunk id),不要把 Milvus/ES 里的原始内容整体搬进 Redis 再做一次向量匹配,那是重复造轮子。
- 多品牌场景下,[1]~[9] 所有 Key 都必须带 `brand`/`channel` 维度,建议在设计阶段就统一 key 生成函数,避免后期到处补前缀。
- 每个环节都建议先用 Redis 的 `INFO` 和自定义埋点观察真实命中率,再决定要不要为某个环节加复杂度 —— 不是每个箭头都值得做缓存。
